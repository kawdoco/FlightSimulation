# MVC implementation baseline

The React application is the View. REST Controllers handle HTTP transport and validation; Services own business rules; Repositories persist the Model (JPA entities). Request DTOs belong in dto and must exclude server-owned IDs, status and timestamps. Controllers must not call repositories directly.

Implemented in this increment:
- Validated device-registration DTO with explicit entity mapping.
- Configurable frontend origin for REST and WebSocket.
- Configurable frontend backend origin via VITE_BACKEND_URL (including WSS when HTTPS is used).
- Missing telemetry flight responses use the existing 404 handler.
- Invalid business arguments return 400; database integrity conflicts return sanitized 409 responses.

Remaining enterprise work is tracked in ENTERPRISE_READINESS_REVIEW.md. Authentication is still open and this increment is not a production-readiness certification. Identity, role permissions and authenticated WebSocket integration must ship together with the frontend login flow. Persistent schema migrations, concurrency protection and bounded telemetry require additional implementation and integration tests.

Maintenance work orders are now implemented through MaintenanceController -> MaintenanceService -> MaintenanceRepository. Validated creation accepts an existing aircraft and a description; paginated listing returns 50 records per page. Status transitions enforce OPEN -> IN_PROGRESS -> COMPLETED and record completion time. Optimistic locking protects simultaneous updates. The React maintenance page supports creation, listing, pagination and transitions with loading/error states. Work orders do not automatically release or ground aircraft; aircraft operational status remains separately managed. Authentication and production schema provisioning remain pending. Service tests cover unknown aircraft, invalid transitions and completion timestamps; browser and database integration tests remain pending.

## Authentication baseline
The UI now requires sign-in. REST uses stateless HTTP Basic authentication; the frontend holds credentials only in memory and clears them on sign-out. STOMP CONNECT authenticates the same credentials, permits telemetry subscriptions only, and rejects client publishing. Deploy behind HTTPS/WSS: Basic credentials must never travel over public plaintext connections.

Before starting backend, set APP_ADMIN_PASSWORD to a unique password of at least 12 characters. Username: admin. No default password is shipped. Startup fails if this configuration is missing. Current bootstrap user is in memory; durable user administration, additional users, identity-provider integration, password rotation, rate limiting and security integration tests remain pending.

Server permission rules: VIEWER/OPERATOR/ADMIN can read; OPERATOR/ADMIN can mutate; only ADMIN can delete. Only the bootstrap admin is provisioned in this increment. All users currently share aircraft visibility; tenant/ownership restrictions are not implemented.

Existing service tests and frontend production build pass. These checks compile the new security code but do not verify live login, CORS or STOMP authorization. Authentication is a baseline, not completed enterprise identity management.

Security verification: six Spring Boot/MockMvc integration tests now cover anonymous denial, invalid credentials, admin login, viewer read access, viewer write denial and operator delete denial against an isolated in-memory test database. These do not cover live WebSocket authentication. Frontend simulator is now lazy-loaded with an accessible loading status; the initial JavaScript bundle decreased from approximately 1,352 kB to 370 kB, with a separate approximately 981 kB simulator chunk. The simulator chunk still triggers Vite size warnings.

Persistent identity increment: ApplicationUser and UserRepository now persist BCrypt password hashes and roles. AccountService supplies REST/STOMP identities from the database. Initial admin provisioning only creates a missing admin; APP_ADMIN_PASSWORD no longer resets an existing account on restart. The authenticated /api/auth/password endpoint validates current credentials and accepts new passwords of 12–128 characters. The UI change-password form signs the user out after success. Existing authenticated WebSocket sessions are not immediately revoked by password changes; connection revocation, user administration, rate limiting, schema migrations and live WebSocket tests remain outstanding. Production schema must include application_users before using ddl-auto=validate.

Admin user management: /api/users is now restricted to ADMIN for every HTTP method. Paginated responses expose only username, role and enabled state. Admins can create users with a validated initial password, change roles and disable accounts. Own-account and bootstrap-admin changes are rejected to avoid accidental lockout. REST authentication and new STOMP connections reject disabled accounts; existing STOMP connections still require revocation work. The Manage users panel is visible after admin login. Existing local schemas receive enabled=true by default; production requires an explicit schema migration before restart.

Workflow verification: WorkspaceWorkflowTest passes against an isolated transactional H2 database. It exercises user creation, sign-in, incorrect-current-password rejection, password change, old-password denial, new-password success and disabled-account denial. Maintenance verification exercises creation, invalid transition rejection, work start, completion timestamp and viewer listing. Transactions roll back fixture changes. Browser click/visual verification remains outstanding because the computer-use inventory exposed no browser or app surfaces.

WebSocket revocation increment: transport sessions are tracked and bound to the username authenticated by STOMP CONNECT. Password changes and account role/enabled changes publish transaction events; after successful commit, matching local-process sockets close with POLICY_VIOLATION. Other accounts remain connected and closed sessions are removed. Existing backend suite passes; two additional registry tests verify account-specific closure and disconnect cleanup. Live STOMP reconnect and multi-instance cross-node revocation remain unverified/unimplemented. This registry is local to one backend process.

Input/concurrency verification: entity identifiers are read-only in HTTP JSON binding, as are flight start/end timestamps and telemetry recordedAt. Operator-supplied identifiers therefore cannot choose persisted aircraft IDs; an HTTP integration test verifies this. This is targeted mass-assignment protection, not a complete DTO conversion. A two-thread database integration test verifies that existing optimistic versions allow exactly one of two flights for the same aircraft to start; the losing transaction is rejected and only one IN_PROGRESS flight persists. Verification uses H2; PostgreSQL concurrency validation remains pending.

Telemetry summary now executes database COUNT/AVG/MAX/MIN aggregates instead of materializing every sample in Java. Response keys and zero values for empty flights are retained. A flight_id/recorded_at index is declared for local schema update; production requires explicit migration and query-plan verification. Two database tests verify empty-flight behavior and exclusion of samples belonging to other flights. Full backend suite: 26 passing tests. History retrieval and CSV export remain unbounded and need pagination/streaming; this change improves summary application memory use only, not all telemetry operations.

Telemetry history pagination: GET /api/telemetry/{flightId}/history accepts page (>=0) and size (1–200, default 100), returns content/page/size/hasNext, and sorts by recordedAt descending then id descending. Uses Slice to avoid a total-count query. Report UI requests 100 samples per page with previous/next controls; summary remains flight-wide. Database tests cover bounded pages, flight scoping, no overlapping records and invalid limits. Existing legacy list endpoint and CSV export remain unbounded for compatibility; ongoing ingestion may shift offset-based pages, so these pages are not a fixed snapshot.

CSV export now returns StreamingResponseBody and reads at most 500 telemetry records per query using a descending ID cursor. The maximum ID is captured before streaming so later inserts do not extend a running download. Metadata fields are CSV quoted, quotes doubled and spreadsheet formula prefixes neutralized. Output uses UTF-8/CRLF. Flight existence is checked before the response starts. Export order is descending insertion ID; deletes/updates during export are not a transactional snapshot. Backend memory is bounded by batches; frontend Axios still buffers the completed download as a Blob. Legacy telemetry list remains unbounded. CSV escaping and cursor batching tests pass; actual large downloads/browser behavior remain unverified.

HTTP CSV verification: TelemetryDownloadTest passes three integration tests using an isolated committed H2 database and MockMvc async dispatch. A 501-record download crosses the 500-row batch boundary and verifies all 501 unique samples, metadata escaping, Content-Disposition, content type and successful async completion through the security filters. Separate tests verify anonymous denial and a missing-flight 404 before streaming starts. These are HTTP application integration tests, not a live browser download or production load test; browser Blob buffering remains unchanged.

API error contracts: malformed JSON, invalid parameter types and missing required query parameters now return safe 400 responses with an error message. Validation responses retain field-specific keys and add an error summary for clients that read response.data.error. Four HTTP integration tests verify these cases; security test class now contains 13 passing tests. No generic catch-all handler was introduced, preserving framework authorization handling.

Serial reliability increment: enabled serial input now connects on a daemon worker and retries unavailable/disconnected ports every three seconds; missing hardware no longer prevents HTTP startup. Serial frames retain at most 4096 characters; oversized frames are discarded through the next newline before processing resumes. Four framing tests cover CRLF, EOF, exact limit and oversized recovery. Backend suite passes. Physical unplug/replug and shutdown behavior require ESP32 verification; no hardware reconnect test has been performed.

Telemetry freshness UI: Telemetry and IoT pages show waiting/live/stale states based on browser receive time. After ten seconds without a new packet, retained values are explicitly labeled stale; the last receive time remains visible. New packets restore live status. The clock runs inside the status component to avoid re-rendering the 3D scene every second. Four Node tests verify freshness boundaries and recovery, now included in local verification and CI. This measures received data freshness, not hardware connectivity or packet authenticity.

Frontend authentication recovery: matching authenticated REST 401 responses clear in-memory credentials and return to sign-in with an explanation. A late response for older credentials cannot clear a newer login, and 403 permission denials retain the login. Default API timeout is 30 seconds; CSV download explicitly allows five minutes. Fetch telemetry writes also enforce a 30-second timeout and handle 401. Four session policy tests plus four telemetry freshness tests pass; production build passes. These are policy unit tests, not browser interaction tests. WebSocket-only credential rejection still relies on a subsequent REST response for sign-in recovery.

Aircraft and flight create/update requests now bind validated request records instead of JPA entities. Explicit mapping excludes IDs, versions, relationships and flight lifecycle fields; text fields are limited to 255 characters and trimmed. Flight status/timestamps remain service-owned and aircraft selection remains the aircraftId parameter. Existing frontend request shapes remain accepted. HTTP workflow tests verify server-managed flight state cannot be injected and oversized aircraft text returns 400. Full pre-addition suite and both added contract tests pass. Response entities and telemetry/alert request DTO conversion remain pending.

Telemetry and alert writes now use explicit validated request records. Telemetry mapping excludes flight relationships, IDs and recorded timestamps; REST values must be finite and satisfy existing ranges. Alerts validate type/message lengths and severity, exclude lifecycle fields and require any associated flight to belong to the selected aircraft. Existing suite and three additional mapping/validation/association tests pass. Finite-number DTO validation covers REST requests; equivalent serial-packet finite validation still needs review.

Serial packet numeric validation now rejects NaN and positive/negative infinity in every telemetry field before conversion, persistence or broadcast. Tests exercise all 21 non-finite field/value combinations, finite boundary acceptance and missing-value rejection. The full backend suite passes. These validator tests do not substitute for physical sensor fault injection.

Credential redaction: password-bearing request records now redact toString output and mark password fields JSON write-only. ApplicationUser passwordHash is JSON-ignored as a second layer beyond the safe user response DTO. Four tests verify request/entity serialization, redacted string output and successful password deserialization. This prevents accidental object/string exposure; raw HTTP body capture, proxy logging and Authorization header logging still require appropriate operational configuration.
